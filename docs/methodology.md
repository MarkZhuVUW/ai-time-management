# 全历史工作流审计方法

本任务要找出“经常要重新检查、比较、确认或执行的事情”，再判断 App 或 ChatGPT 定期任务能否减少投入。主题热度不是低效证据。一个人谈股票很多，可能是在学习、享受研究、解决一次复杂问题，也可能是每天重复查同样的公告；这几种行为不能合并成同一种“浪费”。

当前四个候选方案只来自本线程已经确认的两个机器人及其邻近需求，**不是完整历史归纳，也不是最终项目排名**。最终必须从实际导出重新发现工作流，包括与股票和 Powershop 无关的领域。

## 1. 先建立覆盖清单，再讨论“全部”

用户指定全部历史为主，最近 90 天显示当前变化。实际可分析范围由已提供的文件决定，而不是由 ChatGPT 账户名称或登录状态决定。

每个来源在本地记录：来源别名、账户/工作区别名、导出时间、文件格式、最早/最晚可用日期、会话数、有日期消息数、缺失日期数、是否缺分支指针，以及用户已知的缺口。只记录必要别名，不把邮箱、工作区敏感名称或原文提交 GitHub。现有 CLI 可一次读取多个 JSON/ZIP/JSONL，跨来源按 conversation_id + message_id 去重，保留来源序号与重复/冲突计数；用户不必手工合并。若自制规范化数据使用简单 ID，应为不同来源加前缀，避免误碰撞；正常导出中的同一消息则保留共享 ID，以便识别跨次导出的重复。合并数量不证明覆盖了所有账户或模式。

chat、work、Codex 的记录是否在同一导出里，需要实际核对；不假设一份导出覆盖所有模式。无法导出、已删除、临时聊天、其他工作区不可访问等情况记为“未知/缺失”，不能臆测它们的数量、内容或发生频率。没有记录不等于没有做过该工作。

全历史图中的起止日期是导出可观测范围。若已知某段时间缺数据，应标记缺口，不能把缺口当零活动。尚不知道缺口时，日历周均值只能称“该导出窗口内的观测周率”，不称用户真实生活频率。导出时间早于审计时点的部分应单列说明，以免因陈旧导出稀释当前频率。

## 2. 全领域发现：目录是搜索框架，不是用户画像

先扫描全部可读用户消息，不能只搜索 SEC/Powershop 然后宣布找全。下列 20 个领域用于检查遗漏；只有实际历史出现证据，才进入个人报告。领域交叉时允许多标签，工作次数要另外去重。

| 发现领域 | 检查历史中是否存在的重复工作，而不是假定用户有该需求 |
| --- | --- |
| 证券与投资研究 | 同一关注对象的公告核对、条件变化、数据更新 |
| 银行、支付与个人账务 | 对账、到期、费用或汇率条件比较 |
| 电力、水、网络与其他公用服务 | 优惠是否适用、覆盖是否够、账单是否异常 |
| 订阅和会员 | 续费、价格变化、是否仍在使用 |
| 购物和耐用品 | 固定清单的价格/库存/保修变化 |
| 出行和旅行 | 已确定行程的价格、入境规则或延误变化 |
| 住房与物业 | 定期费用、保养、材料与维修跟进 |
| 工作信息与协作 | 反复汇总同一数据、待办状态和决策材料 |
| 研究、学术与文献 | 固定问题的新证据、新论文和截止日期 |
| 软件开发与部署 | 重复环境检查、构建发布、依赖或运行异常 |
| AI 工具与模型使用 | 固定需求的能力、费用或接口变化 |
| 求职、职业与资质 | 符合条件的机会、新要求、到期维护 |
| 学习与语言 | 重复练习可否按明确反馈安排；探索性学习不算浪费 |
| 新闻与公共事务 | 固定主题是否出现实质新事件，能否减少反复搜索 |
| 健康与生活管理 | 用户明确安排的记录、预约或补给；不自动作医疗判断 |
| 运动与训练 | 已有计划的执行汇总、器材或场地信息变化 |
| 饮食与家庭补给 | 固定偏好下的采购、库存或重复计算 |
| 行政、税务与合规 | 文件到期、材料清单、已知申报步骤跟踪 |
| 内容、创作与社交运营 | 重复整理、发布准备、指标汇总；不把创作本身当低效 |
| 社群、兴趣与娱乐 | 固定活动/更新的筛选，避免给休闲额外制造任务 |

现有 `audit.history` 提供 17 个中立主题加 `uncategorized` 的关键词初筛，涵盖财务、软件、职业、学习、购物、旅行、健康、家庭能源、行政、效率、饮食、文娱、人际与时事等；它们不是已经发现的用户兴趣，也不与上面的 20 个探索领域逐一对应。初筛提供可重复的计数，不承担全领域语义归纳。最终分析需对分类和未分类内容做本地审阅，并按真实新领域扩展规则；未完成这一步前不能说“所有问题已归纳”。不会为了补齐目录捏造个人兴趣。

## 3. 用“工作签名”替代“关键词出现次数”

每个有潜在价值的候选建立结构化工作签名：`对象 / 触发条件 / 用户要决定什么 / 输入来源 / 必须得到的产物或动作 / 完成条件`。例如，只有历史支持时才建立“某组关注公司 / 新申报 / 是否需要进一步研究 / 官方公告 / 去重变化卡 / 已读到原文并完成判断”。“股票”“便宜”“比较”三个词同时出现并不能确定同一个工作流。

至少区分四个单位：

| 单位 | 可以观测或推断什么 | 不能直接推出什么 |
| --- | --- | --- |
| 用户消息 | 一条真实提问及其时间 | 一次独立工作、花了几分钟 |
| 对话/推断交互会话 | 一段讨论；工具以同对话间隔 20 分钟初分段 | 20 分钟实际用时、全部劳动投入 |
| 工作事件 | 同一对象与目的的一次检查/决定，经上下文审阅确认 | 等同某一主题消息条数 |
| 可替代工作事件 | 扣除已被现有工具处理、主动研究和必须人工判断的部分 | 所有工作事件都应自动化 |

同一会话问 10 轮代码报错可能只是一次新项目调试；隔几周反复问相同账户状态可能是周期工作。长间隔不是独立任务的充分证据，短间隔也可能包含两个不同对象。先用时间/对象/目的生成候选分组，再抽查，不能把规则当事实。

每项至少保留一种反例：该主题中哪些记录不是可替代工作。这能检验分类器是否只是在给兴趣贴上“低效”标签。跨聊天但同一时点、同一来源、同一决定的记录归同一事件；跨多主题讨论的事件可以多标签，但工作收益只能分配一次。

## 4. 证据索引与置信度

原文只在 `private/` 留存。审阅时用本地消息哈希引用和会话哈希引用定位上下文，旁边记日期、工作事件编号、纳入/排除原因、领域与规则版本；不能仅保存一段脱离上下文的关键词。分享版可只保留事件编号、汇总与必要哈希引用。哈希不是完全匿名，日期与主题仍可能敏感，提交前审阅。

当前导入器输出 `evidence_index`，不包含原文或原始 ID。可选 `--private-review private/question-review.json` 单独保存私有提问片段，只允许写入当前工作目录下的 `private/`，不会混入汇总。按“主主题 × 最近90天/更早/无有效日期”分层，每层最多 100 条，每条最多 2000 字符，使用确定性哈希抽样，并记录总体、样本与截断情况。它帮助发现未知工作流，但抽样和仅有用户提问的片段不代表已审阅全部上下文；对候选与反例仍需回看原始导出，包括必要的助手答复。工作事件标签和“可替代”判断是下一阶段审阅结果，尚未由导入器自动生成。不把私密审阅文件提交 GitHub，也不把全文发送给新的外部服务。

| 证据等级 | 报告写法 |
| --- | --- |
| 计数已测 | 导出中可复算的消息/日期计数，附覆盖说明 |
| 工作事件已审阅 | 已查上下文并归并的事件，写明抽查数量和争议项 |
| 自动化需求待验证 | 有重复工作迹象，但没有确认现有系统缺口或数据源 |
| 用时已测 | 少量真实执行样本，保留范围和样本数；不因有次数就升级为已测用时 |
| 用时假设 | 用户未提供执行时长，给区间和敏感性分析，不使用“实际浪费”措辞 |
| 已实现收益 | 在实际试运行中同时观察基准、自动化覆盖、阅读、维护和异常；仅有代码通过测试不够 |

若审阅发生争议，先报告工作事件的下限/上限和原因，不用小数精度掩盖定义不清。收益场景区间表示参数敏感性，不是统计置信区间。

## 5. 尽量从历史解决问题，不向用户发长问卷

先从历史直接提取：反复出现的对象和网站、使用时区、用户已经写明的阈值、目前用的工具、此前拒绝的办法、已经完成的自动化、重复检查后的下一步动作。保留原始日期：几年前的偏好不自动沿用，已停用服务不列为新项目。

再对候选工作抽取完整上下文，解释“为什么用户不得不再次问”。可能的根因包括没有状态保存、没有可靠信息源、结果变化了、通知太多、购买/执行失败、不同网站要来回核对，或只是用户愿意再研究。只有前几种明确流程缺口才进入自动化设计。

最终最多针对排名靠前的两项问真正影响实施的缺口，例如“现有机器人是否已处理改报”或“哪个名单是当前仍关注的”。能通过用户已经提供的记录回答的，不重复问；账号密码与原始支付凭证不在聊天里索要。

时间校准可选，只对最有希望的工作收集约五次真实执行：从开始检查到形成决定的主动投入、等待是否占用注意力、最后是否仍需手动处理。可以使用已有运行日志、浏览记录摘要或用户给的区间；不要求用户永久记录每天每件事。不愿校准时维持假设标签，做门槛分析，不声称准确到分钟。

## 6. 全历史和最近 90 天各回答不同的问题

全历史用于发现长期习惯、曾经自动化的事、季节性任务和已经解决的问题；最近 90 天用于判断当前优先级。两个窗口都同时给出消息数、工作事件数、覆盖日历天数和规范化每周率。不能拿九年的总数与 90 天总数直接比较。

按周看稳定性与突发性：一个月内集中上百条开发问题可能是单次项目，连续多月每周两次同样核对更适合持续自动化。季节性任务按其实际触发周期核算，不能把年审平均到每周之后误判它不重要。若过去有很多、最近已没有，先核实是否已解决，避免重新制造一个服务。

频率趋势只说明观察到的提问变化；线下劳动、其他聊天平台或导出缺口仍未知。需要区分“未观察到”和“确认不再需要”。

## 7. 从真实工作事件选择 App 或定期任务

每项先写最小替代链：`触发→读取可信输入→去重和状态→规则判断→输出/执行→确认结果→异常恢复`。只自动采集而把筛选负担全交回用户，可能没有节省。输出必须减少主动打开、重复比较或确认的次数，而不是新增一份必须读完的日报。

- 公开信息、低频、容许人工判断、无需精确跨次状态：先考虑 ChatGPT 定期任务，验证账户能力与推送负担。
- 账户数据、连续监测、精确去重、执行/支付、审计或可靠重试：优先扩展现有 App。先核实官方接口或用户可合法访问的来源，不能凭想象指定 API。
- 即时讨论、创作、学习、一次性诊断：通常保留交互，不自动化讨论本身。
- 现有软件已覆盖：配置现成产品或复用已有代码，不为一次低频检查造新客户端。

每个方案写“如果无变化会怎样”：App 默认不发无意义消息，定期任务若无法静默，就改低频或放弃。重要触发阈值、缺失数据行为与恢复检查应可审阅；购买和对外发消息不因本次研究自动获得执行授权。

## 8. 时间模型、回本门槛和成本口径

当前模型只计算**现有自动化之外**的增量人工检查，公式与 `audit/economics.py` 对齐：

`每周净省分钟 = 增量检查次数 × 可替代比例 × (原每次分钟 − 自动后每次审核分钟) − 每周维护分钟 − 每周异常处理分钟`

剩余未被替代的检查仍占时间，不能假设消失。若无变化摘要也要读、固定周报要整理，应另列固定阅读成本纳入维护/运营参数，不能漏掉。原始频率为 0 或不明时不补成高频场景；不明需要标记，不用图表暗示已测。

`回本周数 = 建设分钟 ÷ 每周净省分钟`；净省≤0 时写无法回本。`12周回本所需每周检查次数 = (每周维护与异常分钟 + 建设分钟/12) ÷ [可替代比例 × (原每次分钟 − 新每次审核分钟)]`。分母≤0 则该方式没有节省机制。12 周是可修改决策策略，不是用户已给出的回本要求。

开发、集成、测试、部署和之后的维护分开列；现金费用另算，不把电费优惠金额当作时间收益。用保守参数仍为正、在用户接受周期内回本才优先做；若主要收益是可靠性、避免漏买或降低风险，另设目标，不冒充时间节省。

### 当前预算口径

`data/scenarios.json` 的建设情景已与 `docs/automation-designs.md` 的完整方案粗估范围统一。全部成本、频率、用时和覆盖率仍未经真实历史、现有源码或实际集成验证，不是确认报价：

| 候选 | 计算器建设情景：低/中/高 | 设计文档的待验证预算 | 使用限制 |
| --- | --- | --- | --- |
| 股票变化摘要 | 6 / 10 / 16 小时 | 6–16 小时 | 多来源接入与关注名单仍需验证，不能宣传确定回本 |
| SEC 增量整理 | 4 / 8 / 12 小时 | 4–12 小时 | 改报、脚注和去重能否复用现有能力仍未知 |
| Powershop 补缺 | 4 / 8 / 12 小时 | 4–12 小时，仅只读 | API/页面与真实账单未核验，不含新增交易流程 |

按本次文件中的中央参数，三项回本分别约 28.6、46.2、480 周，与当前 `reports/summary.json` 一致；这些只是当前假设的计算结果，不是用户已实现的节省。频率、维护或建设范围改变后必须重新运行报告，不能沿用这些数字。最终立项前按选定范围重新预算，不摘取乐观参数宣传 ROI。异常监控未进入当前情景文件，没有可相加的数字。

## 9. 淘汰规则比多提方案更重要

以下任一情况成立就暂不做：没有重复检查证据；只是一次项目/主动学习；已有工具覆盖；预计新阅读与维护比旧工作更多；没有可用的数据来源；决策高度依赖每次重新理解而规则不稳定；保守净收益为负且没有另行认可的可靠性价值。

可把“连续四周有同类事件、至少五次基准抽样、保守收益为正”作为初筛策略，再对低频高价值的季节事件单独处理。这些是可调整门槛，不是从当前历史算出的个人规律。不要为了凑五个方案把已经淘汰的东西换个名字重新推荐。

## 10. 导出到手后的最终交付

1. 输出覆盖审计与异常记录，确认哪些账户/工作区、时间段实际纳入。
2. 对全部消息初筛，审阅未分类领域；建立工作事件与证据索引，给出纳入和排除样例。
3. 给出全历史、最近 90 天的频率表；消息、会话、实际重复工作分别列，不能混轴。
4. 仅对真实重复且仍未被现有系统处理的工作建收益模型。给出估算区间，标注哪些分钟数未测。
5. 最终只保留少数值得做的方案，逐项交代 App/任务形式、触发、数据来源、输出、维护、预计回本和不做的理由。先做一项低成本试验，避免并行堆积系统。
6. 制作基准/优化后的每周主动投入柱状图及净节省图，假设用醒目标记；阴影/误差线只表示情景范围。对于无真实频率的条目继续标“缺数据”，不填零、不与已测项目混排。
7. 实际试运行后复核新增通知、漏报、异常与维护时间，再升级为“观察到节省”。将阶段、参数、证据与验证命令写进 `PROGRESS.md`，提交经过隐私检查的汇总。

当前完成的是方法与工具准备，不是第 1–7 步已经跑完。历史到达后，真正的新领域与新工作流必须能改变现在的候选名单；不能把当前两个既有机器人的扩展硬套成全历史答案。
